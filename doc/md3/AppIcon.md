# Application logo and packaged icon

This article documents the fork's own application mark, its committed vector
master, the generated raster derivatives, where each is wired into the built
application, and what still needs a change outside this lane's allowed files
to finish wiring it into the Windows installer.

It also documents the two follow-ups the mark's original lane deferred: the
About-dialog splash background, and the Explorer file-type-association
icons for `.vbox`/`.vbox-extpack`/`.ova`/`.ovf`/`.vdi`/`.vmdk`/`.vhd`/`.hdd`.
Both are now original artwork, generated by the same script, from the same
documented palette, with no Oracle trademark remaining in either.

## Why this exists

The release checklist for this fork requires an original, project-appropriate
logo and a real packaged application icon: a committed master source, valid
generated platform formats (including a multi-resolution `.ico` for Windows),
the mark wired into application chrome/executable/installer/update metadata,
and verification of the built artifact at both small and standard icon sizes.
A framework default icon, a missing mark, a mutable/unreachable icon URL, or a
raster file renamed to an icon extension all block that gate.

The icon this fork shipped with until now was Oracle's own trademarked
VirtualBox mark (`src/VBox/Artwork/OSE/virtualbox.svg`, a teal/orange
checkmark authored 2024-08-22, upstream commit `d5ed5ae5694`). That is not
this project's mark to ship, so it has been replaced with an original design.

## The mark

A rounded Material 3 "container" square, filled with this fork's own
generated seed colour (`#6750A4`, see [`TonalPalette.md`](TonalPalette.md)),
holding two overlapping rounded "window" panes -- a light lavender pane
(`#D0BCFF`, the fork's own documented Primary-80 tone) behind a white pane,
separated by a thin gap in the background colour. It reads as one machine's
window running another's: a host surface with a guest surface layered on top,
which is what the application actually does. The whole mark is three flat
shapes with no gradients or fine detail, so the silhouette still reads at
16x16.

| Colour | Hex | Role |
| --- | --- | --- |
| Container / gap | `#6750A4` | Fork's generated Material seed (documented in `TonalPalette.md`) |
| Back pane | `#D0BCFF` | Fork's own documented Primary-80 tone |
| Front pane | `#FFFFFF` | Maximum-contrast foreground |

## Committed master and generator

- **Vector master:** [`src/VBox/Artwork/OSE/virtualbox.svg`](../../src/VBox/Artwork/OSE/virtualbox.svg).
  This is not a new file living alongside the old one -- it *is* the file the
  build already resolves through `Config.kmk`'s `VBOX_BRAND_GUI_VBOX_SVG` and
  loads at runtime via `QIcon(":/VirtualBox.svg")` in
  `UIVirtualBoxManager.cpp` (the VirtualBox Manager window icon), so replacing
  its content in place rewires that chrome with no build-script edits needed.
  It is committed, static, and requires no network access or external tool to
  resolve -- opening it is the whole story.
- **Reproducible raster generator:**
  [`src/VBox/Artwork/generate-icon-assets.py`](../../src/VBox/Artwork/generate-icon-assets.py).
  A small, dependency-light (Pillow only) script that draws the *exact same*
  coordinates as the SVG master and renders every derived PNG and the Windows
  `.ico` from one supersampled render pass. It also generates the
  About-dialog splash background and the eight file-type-association icons
  documented further down this article, from the same documented palette.
  Run it from the repository root with
  `py -3 src/VBox/Artwork/generate-icon-assets.py` to regenerate every
  raster derivative deterministically after the master (or the palette,
  or the file-type designs) changes. It makes no network calls.

## Where the mark is wired in

| File | Consumer | Wiring point |
| --- | --- | --- |
| `src/VBox/Artwork/OSE/virtualbox.svg` | VirtualBox Manager window icon | `QIcon(":/VirtualBox.svg")` in `UIVirtualBoxManager.cpp`, resolved through `VirtualBoxBrand.qrc` -> `Config.kmk`'s `VBOX_BRAND_GUI_VBOX_SVG` |
| `src/VBox/Frontends/VirtualBox/images/OSE/VirtualBox_{16,20,32,40,48,64}px.png` | Window/taskbar icon set on non-Windows chrome | `VirtualBoxBrand.qrc` -> `VBOX_BRAND_GUI_VBOX_*PX_PNG` |
| `src/VBox/Frontends/VirtualBox/images/OSE/about_16px{,_x2,_x3,_x4}.png` | Small About-dialog mark (16/32/48/64 px) | `VirtualBoxBrand.qrc` -> `VBOX_BRAND_GUI_ABOUT_16PX*_PNG` |
| `src/VBox/Artwork/win/OSE/VirtualBox_win.ico` | The real Windows executable icon | `Config.kmk`'s `VBOX_WINDOWS_ICON_FILE` (OSE build), embedded via `VBOX_SET_VER_INFO_EXE`/`VBOX_SET_VER_INFO_DLL` and the generated `*-icon.rc` resource scripts into **every** Windows PE the build produces: `VirtualBox.exe` (Manager), `VirtualBoxVM.exe`, `VirtualBoxHardenedVM`, `VBoxSVC`, `VBoxSDS`, `VBoxStub`, `VBoxHeadless`, `VBoxSDL`, `VBoxService`, `VBoxNetDHCP`, `VBoxNetNAT`, `VBoxIntNetSwitch`, and more -- anything that pulls in `$(VBOX_WINDOWS_ICON_FILE)` |

Because `VBOX_WINDOWS_ICON_FILE` and the `VBOX_BRAND_GUI_*` variables in
`Config.kmk` are fixed, already-existing paths, replacing the *content* at
those paths was enough to rewire the whole chrome and every packaged Windows
executable -- no edit to `Config.kmk` itself was necessary or made.

## Windows `.ico` verification

`src/VBox/Artwork/win/OSE/VirtualBox_win.ico` is a real, structurally valid
Windows icon, verified two independent ways (the generator's own hand-rolled
directory reader, and an unrelated Pillow load):

- **Signature:** first 6 bytes `00 00 01 00 07 00` -- reserved=0, type=1
  (icon), 7 directory entries. This is the mandatory `ICONDIR` header; a PNG
  renamed to `.ico` would not have it.
- **Directory entries** (all 32bpp, PNG-compressed payloads, each payload's
  own PNG signature `89 50 4E 47 0D 0A 1A 0A` verified present):

  | Size | Payload bytes | PNG-compressed |
  | --- | --- | --- |
  | 16x16 | 634 | yes |
  | 24x24 | 918 | yes |
  | 32x32 | 1170 | yes |
  | 48x48 | 1662 | yes |
  | 64x64 | 2240 | yes |
  | 128x128 | 4669 | yes |
  | 256x256 | 9688 | yes |

- **Independent cross-check:** `PIL.Image.open(...).info['sizes']` reports
  `{(16,16),(24,24),(32,32),(48,48),(64,64),(128,128),(256,256)}` and loads a
  256x256 RGBA default frame -- confirms Pillow's own ICO parser agrees with
  the hand-rolled directory reader used above.
- **Legibility at small size:** at 16x16 the mark is a solid purple rounded
  square with a visible lighter pane peeking from behind a white pane -- the
  two-pane silhouette still reads; there is no fine detail to lose.

## About-dialog splash background

`src/VBox/Frontends/VirtualBox/images/OSE/about.png` (and its `_x2`/`_x3`/`_x4`
variants, 640x480 up to 2560x1920) used to be Oracle's full "VirtualBox"
wordmark splash graphic -- white/orange logotype on a teal gradient field --
used as the whole background of the About dialog. It has been replaced with
original artwork, generated by the same `generate-icon-assets.py` script
(`render_about_master()` / `write_about_variants()`).

**Where it is wired in and why the layout looks the way it does:**
`VBoxAboutDlg::prepare()` (`src/VBox/Frontends/VirtualBox/src/VBoxAboutDlg.cpp`)
loads `:/about.png` (resolved through `VirtualBoxBrand.qrc` ->
`Config.kmk`'s `VBOX_BRAND_GUI_ABOUT_PNG`) at a fixed **640x480 logical**
size -- the `_x2`/`_x3`/`_x4` files are plain device-pixel-ratio variants of
that same canvas for HiDPI, not different compositions. `paintEvent()` draws
it as the entire dialog background with no further compositing, and
`prepareLabel()` then overlays a bottom-right-aligned `QLabel` in
`Qt::white` (by default; brandable via `UI/AboutTextColor`) carrying the
product name, version, host platform and copyright line. So the artwork had
two real constraints: it needed to *not* be Oracle's, and the bottom-right
quadrant needed to stay dark enough for that white text to read.

**The composition:** a diagonal Material 3 gradient field (Neutral N6
`#141218` to Neutral N17 `#2B292F`), two soft blurred accent shapes
(Primary-container `#4F378A` and Primary-80 `#D0BCFF`, both at low alpha,
biased away from the text zone), and the application mark itself --
literally the same `SHAPES` geometry as the app icon, reused via
`draw_mark()` -- placed large and left-of-centre. **It deliberately carries
no wordmark or product name.** This fork's own display name and typography
are a separate, not-yet-settled decision (see "what the mark's original
lane deferred" above, now folded into this article); baking a guessed name
into a raster here would fight whatever that later decision picks. The
dialog's own `QLabel` already carries the real product name and version at
runtime, in whatever text the build is configured with.

Measured bottom-right-quadrant average colour on the generated `about.png`:
RGB `(40, 38, 44)` -- close to the N6 base tone, giving the overlaid white
text roughly 14:1 contrast, well clear of WCAG AA.

## File-type-association icons

The eight Explorer file-type icons under `src/VBox/Artwork/win/` --
`OSE/virtualbox-vbox.ico`, `OSE/virtualbox-vbox-extpack.ico`,
`OSE/virtualbox-ova.ico`, `OSE/virtualbox-ovf.ico`, `virtualbox-vdi.ico`,
`virtualbox-vmdk.ico`, `virtualbox-vhd.ico`, `virtualbox-hdd.ico` -- used to
be Oracle's glossy 3-D "box" cube family (a blue cube labelled `vbox`, an
orange cube labelled `vdi`/`ova`, and so on). They have been replaced with
flat Material 3 icons from the same generator (`FILE_TYPE_ICONS`,
`render_file_type_icon()`).

**Where they are wired in:** `src/VBox/Installer/win/Resources/Makefile.kmk`
(out of this lane's editable scope, and not edited) resolves
`VBOX_WINDOWS_ICON_EXT_{VBOX,EXTPACK,OVA,OVF,VDI,VMDK,VHD,HDD}` to exactly
these eight paths for an OSE build, compiles them into `VBoxRes-icons.rc`
as `IDI_FILETYPE_VBOX*` resources, and links them into `VBoxRes.dll`. The
WiX installer definition (`src/VBox/Installer/win/VBoxMergeApp.wxi`, also
out of scope and not edited) then points each `ProgId`'s `Icon` at
`file_VBoxRes.dll` with the matching `IconIndex` (`-201` for `.vbox`,
`-202` for `.vbox-extpack`, `-301`..`-306` for `.ovf`/`.ova`/`.vdi`/`.vmdk`/
`.vhd`/`.hdd`). Exactly as with the app icon, both of those already point at
fixed paths, so replacing file *content* in place was enough -- no build or
installer script needed editing.

**Design:** all eight share the app mark's own rounded-square container
(radius 56 on the 256-unit grid) so they read as one family, split into two
sub-families so a disk image never looks like a machine definition:

| File | Format | Family | Glyph | Container tone |
| --- | --- | --- | --- | --- |
| `virtualbox-vbox.ico` | `.vbox` machine settings | Package | App mark's own window panes | Seed `#6750A4` |
| `virtualbox-vbox-extpack.ico` | `.vbox-extpack` extension pack | Package | Window panes + "add-on" plus badge | Primary container `#4F378A` |
| `virtualbox-ova.ico` | `.ova` appliance archive | Package | Crate tied with a cross-strap | Secondary container `#4A4458` |
| `virtualbox-ovf.ico` | `.ovf` descriptor (XML only) | Package | Plain text page with rule lines | Outline `#948F99` |
| `virtualbox-vdi.ico` | `.vdi` disk image (native) | Disk | Stacked-cylinder disk platter | Seed `#6750A4` |
| `virtualbox-vmdk.ico` | `.vmdk` disk image | Disk | Stacked-cylinder disk platter | Primary container `#4F378A` |
| `virtualbox-vhd.ico` | `.vhd` disk image | Disk | Stacked-cylinder disk platter | Secondary container `#4A4458` |
| `virtualbox-hdd.ico` | `.hdd` disk image | Disk | Stacked-cylinder disk platter | Surface `#141218` |

Every "Package" icon additionally carries a small top-right dog-ear
triangle the plain app mark does not have, so a `.vbox` file icon still
reads as *a file*, distinct from the application icon itself. Container
tones are deliberately paired across the two families (`vbox`/`vdi` both
use the seed colour, being this fork's two "native, first-party" formats;
`vbox-extpack`/`vmdk` share Primary container; `ova`/`vhd` share Secondary
container) and disambiguated by glyph rather than by inventing extra hues
-- every colour used is one already documented in
[`TonalPalette.md`](TonalPalette.md) or above, none invented for this pass.

Icon sizes match the existing convention exactly: the four `OSE/` icons use
`[16, 24, 32, 48, 64, 128]` (no 256x256 -- `Makefile.kmk` carries a
long-standing comment that OSE build boxes' `rc.exe` doesn't support Vista
icons), and the four shared (non-`OSE`-suffixed) disk-format icons use
`[16, 24, 32, 48, 64, 256]`.

### File-type `.ico` verification

Every one of the eight files was verified the same two ways as
`VirtualBox_win.ico` above (hand-rolled `ICONDIR` reader plus an
independent Pillow load), all reporting a valid `00 00 01 00` signature and
every payload PNG-compressed:

| File | Entries | Sizes |
| --- | --- | --- |
| `OSE/virtualbox-vbox.ico` | 6 | 16, 24, 32, 48, 64, 128 |
| `OSE/virtualbox-vbox-extpack.ico` | 6 | 16, 24, 32, 48, 64, 128 |
| `OSE/virtualbox-ova.ico` | 6 | 16, 24, 32, 48, 64, 128 |
| `OSE/virtualbox-ovf.ico` | 6 | 16, 24, 32, 48, 64, 128 |
| `virtualbox-vdi.ico` | 6 | 16, 24, 32, 48, 64, 256 |
| `virtualbox-vmdk.ico` | 6 | 16, 24, 32, 48, 64, 256 |
| `virtualbox-vhd.ico` | 6 | 16, 24, 32, 48, 64, 256 |
| `virtualbox-hdd.ico` | 6 | 16, 24, 32, 48, 64, 256 |

At 16x16 the "Package" family still reads as a two-pane window (or the
document/crate variants) and the "Disk" family collapses to a rounded
block, still distinguishable from one another purely by container tone --
matching how the Oracle originals it replaces were themselves only
colour-distinguishable at that size.

## What this lane deliberately did not touch

A full sweep of `src/VBox/Artwork/` (every file, not just the ones this
lane's task named) turned up four more asset groups that still carry
Oracle's trademarked artwork -- the original checkmark logo or the glossy
3-D "box" file-type cube family. All four are for platforms outside this
fork's active Windows-only delivery scope (the same reasoning the mark's
original lane already applied to the macOS app icon below), so none were
regenerated here, and none needed to be for the Windows release this fork
ships:

- **macOS `.icns` app icon** (`src/VBox/Artwork/darwin/OSE/VirtualBox.icns`).
- **macOS `.icns` file-type icons** (`src/VBox/Artwork/darwin/virtualbox-{vbox,vbox-extpack,ova,ovf,vdi,vmdk,vhd,hdd}.icns`)
  -- the macOS counterpart of the Windows `.ico` set this lane replaced,
  still carrying the glossy cube artwork.
- **Linux/XDG file-type icon PNGs** (`src/VBox/Artwork/other/virtualbox-{vbox,vbox-extpack,ova,ovf,vdi,vmdk,vhd,hdd}-{16,20,24,32,40,48,64,72,80,96,128,256,512}px.png`,
  96 files) -- flat PNG exports of the same glossy cube family, consumed by
  the Linux desktop-integration files (`src/VBox/Installer/common/virtualbox.desktop.in`,
  `virtualbox.mime`, `virtualbox.keys`, `UIDesktopServices_nix.cpp`).
- **Legacy Solaris-only checkmark-logo PNGs** (`src/VBox/Artwork/OSE/virtualbox-{16,20,32,40,48,64,70,128,150}px.png`,
  9 files -- note the plain `virtualbox-*px.png` naming, distinct from the
  `VirtualBox_*px.png` set this lane's predecessor already regenerated).
  These are raster exports of the *old* pre-replacement Oracle checkmark
  logo, not the new mark -- but the only place that still references them
  is `src/VBox/Installer/solaris/Makefile.kmk` (`virtualbox-128px.png` for
  the Solaris `.png` package icon, `VirtualBox_64px.png` for the same
  Makefile's other icon, which *was* already regenerated). Solaris packaging
  is outside the active delivery scope, same as macOS and Linux above.

Per the shared active-scope policy ("preserve historical cross-platform
records ... do not spend current work on them or present them as supported
deliverables"), these are recorded here rather than silently left
undocumented, so a future lane that reopens non-Windows scope has a
starting list instead of having to re-run this sweep.

## Outstanding change needed in files this lane could not edit

The Squirrel.Windows packaging path
(`.github/workflows/windows-package-release.yml` and
`tools/build-windows.ps1`, both out of bounds for this lane) generates a
NuGet `.nuspec` with an `<id>`, `<version>`, `<authors>`, and `<description>`
but **no icon reference at all** -- not a broken/mutable `<iconUrl>`, simply
none. `<iconUrl>` itself would be the wrong fix even if this lane could edit
those files: it requires a live, reachable HTTPS URL, which fails the "not a
mutable or unreachable icon URL" half of the release gate outright.

The correct fix is to pass Squirrel's own `--icon <path>` flag to
`Squirrel.exe --releasify`, pointing at this repository's
`src/VBox/Artwork/win/OSE/VirtualBox_win.ico` (the same file now embedded in
`VirtualBox.exe` itself, so the installer and the installed app agree). That
embeds the icon directly into the generated `Setup.exe`, the Start Menu
shortcut, and the Programs-and-Features entry -- fully offline, no URL
involved. Concretely, both of the following calls need the added flag:

- `tools/build-windows.ps1`, `New-SquirrelInstaller`, the
  `& $Tools.Squirrel --releasify $package.FullName --releaseDir $release --no-msi`
  line.
- `.github/workflows/windows-package-release.yml`, the "Build unsigned
  Squirrel full installer" step's
  `& $squirrel --releasify $package --releaseDir $releaseDir --no-msi` line.

Both need `--icon "<repo-root>\src\VBox\Artwork\win\OSE\VirtualBox_win.ico"`
appended. Neither file was edited by this lane, per its scope boundary; this
is reported here so the lane that owns those files can make the one-line
change.
